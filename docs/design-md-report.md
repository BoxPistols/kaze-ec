# DESIGN.md は何に効いたか — AI 駆動デザインの効果測定

kaze-ec を作る過程で、`DESIGN.md` と `design/screen-spec.json`（機械可読な仕様）
が実際に何を防ぎ、何を防げなかったかの記録。

## 0. 測る前に決めたこと

**後から都合のいい指標を選ばないために、何を測るかを先に固定した。**
効果を後付けで測ると「うまくいった側面」だけを拾えてしまう。

測る対象は次の 4 つに限る。

| # | 測るもの | 判定方法 |
| - | -------- | -------- |
| 1 | 仕様は実装より先に書かれたか | git のコミット順 |
| 2 | 検査は実際に違反を検出したか | 検出→修正のコミット対が履歴にあるか |
| 3 | 検査の網羅範囲に穴はあったか | 穴を塞いだコミットの有無と、その原因 |
| 4 | 人手のレビューでしか気づけなかったものは何か | 検査を通過したのに指摘された事項 |

**測らないもの**: 開発速度、コード量、「AI が書いた割合」。
比較対象（同じものを別の方法で作った場合）が無いので、速い・多いと言っても
根拠にならない。

---

## 1. 仕様は実装より先に書かれたか — 検証済み

git のコミット順がそのまま記録になっている。

```
c49436d  feat: 画面仕様を先に宣言する (screen-spec.json)      ← 仕様
d202ed4  feat: 一覧・商品詳細・決済ウォレットの3画面を実装する  ← 実装
b0cb21c  feat: 仕様↔実装のドリフト検出ツールを追加する          ← 検査
```

宣言が先、実装が後、検査がその後。**この順序でなければ検査は成立しない**
（実装を先に書くと、書いた瞬間に自分のコードが「無申告」になる）。

現在の宣言規模:

| 項目 | 数 |
| ---- | -- |
| 画面 | 4 |
| foundations（設定ファイル） | 2 |
| コンポーネント宣言（のべ） | 25（mui 11 / regenerated 7 / regenerated-tailwind 7） |
| 宣言トークン（ユニーク） | 32 |

---

## 2. 検査は実際に違反を検出したか — 検証済み（4 件）

「一度も何も検出したことがない検査」は動いている証拠にならない。
実際に検出したものを、履歴が残っている順に挙げる。

### 2.1 ハードコード色（意図的に作った実演）

```
931a586  feat: 保留中バッジの視認性を調整する          ← #f5a623 / #fff を直書き
34da328  fix: 保留中バッジのハードコード色をトークン参照に戻す
```

検出内容:

```
[値の不一致] CheckoutWalletPage: 色 #f5a623 が宣言済みトークンのどの値とも一致しない
[値の不一致] CheckoutWalletPage: 色 #fff が宣言済みトークンのどの値とも一致しない
```

これは検出器の動作確認のために意図的に作った。ただし **2.2 以降は意図せず
発生したもの**で、そちらのほうが証拠として強い。

### 2.2 デザイン刷新時のハードコード色（意図せず発生）

マーケットプレイス風にカードを作り直した際、価格オーバーレイとハートの色に
`#fff` を直書きした。検査が 2 件検出し、`theme.palette.common.white` に修正。

### 2.3 Tailwind ハイブリッド化時の無申告（意図せず発生・5 件）

MUI 非依存の部品（TagChip / SearchField / SortSelect）を足したとき、
`screen-spec.json` に宣言せずに使った。

```
[無申告] ItemListPage: TagChip が screen-spec.json に未宣言のまま使われている
[無申告] ItemListPage: SearchField が ...
[無申告] ItemListPage: SortSelect が ...
[無申告] ItemDetailPage: TagChip が ...
[値の不一致] ComponentCatalogPage: 色 #0057B8 が宣言済みトークンのどの値とも一致しない
```

**これが実務上いちばん効いた場面。** 部品を増やすとき、宣言を更新し忘れても
検査が止める。宣言と実装が同時に動くことが強制される。

### 2.4 Hook による即時の差し戻し

`src/pages/**` / `src/theme/**` を編集すると PostToolUse Hook が検査を走らせ、
違反があれば exit 2 で差し戻す。実際に `theme.ts` の primary を `#123456` に
変えて動作を確認した。

```
kaze-ec drift check が違反を検出しました。修正してから続けてください。
  [値の不一致] theme.ts: 色 #123456 が宣言済みトークンのどの値とも一致しない
```

CI 実績: Drift check は success 5 / failure 2。**失敗が 2 回ある**ことが、
検査がゲートとして機能している証拠になる。

## 3. 検査の網羅範囲に穴はあったか — あった（重要）

**DESIGN.md が実態と食い違っていた期間がある。**

当初 DESIGN.md には「トークンやコンポーネント仕様もこのリポジトリには一切
バンドルしていない」と書いていた。しかし実際には `src/theme/theme.ts` に
hex 値が存在し、しかも**検査対象に入っていなかった**。

つまり「kaze-ux 側でトークンが変わっても、kaze-ec の検査は 0 件のまま通る」
状態だった。このリポジトリの存在意義そのものが成立していなかった。

修正（`7dcb48a`）でやったこと:

- `screen-spec.json` に `foundations[]` を追加し、`theme.ts` を検査対象にした
- DESIGN.md の記述を訂正した。「バンドルしていない」のは仕様ファイル
  （tokens.json / components.json / prohibited.md）で、**実行時に MCP を
  呼べない以上、値そのものはコードに残る**。代わりに毎回検証している、と書き直した
- 検証: `theme.ts` の primary を `#0066CC` に変えて検出されることを確認し、戻した

同種の穴がもう 1 つあった。`borderRadius` の検出で、`sx={{ borderRadius: 1.5 }}`
（テーマの倍数指定＝相対値）を絶対値と誤判定していた。相対値はそもそも
ドリフトしないので、正規表現を分けて対象外にした。

### 3.2 免除リストが沈黙していた（2 例目）

効果検証画面（`/effect-lab`）を足したときに、`Table` が
`LAYOUT_ALLOWLIST`（宣言しなくてよい部品の一覧）に入っていることに気づいた。
`Box` や `Grid` と同じ「レイアウト原始要素」の扱いだったが、
**`get_component('table')` は実在する**。DS に仕様がある部品を、検査対象外に
してあった。

allowlist から外した結果:

```
ドリフト検出: 1 件
  [無申告] ComponentCatalogPage: Table が screen-spec.json に未宣言のまま使われている
```

**穴が実際にドリフトを隠していた。** 画面を 1 枚足すまで、この免除は
0 件という結果に紛れて誰にも見えなかった。

残りの免除にも同じ誤りがないかを、allowlist の全 21 件に `get_component` を
投げて確認した。実在したのは `Table` だけで、他は構造的な子
（`CardContent` / `TableRow` / `AlertTitle` など、親が宣言されていれば足りる）か、
DS に存在しないものだった。

そのうえで**この確認を機械化した**（`checkAllowlist`）。allowlist の各エントリに
`get_component` を投げ、実在するものが免除されていたら検査を落とす。
`Table` を allowlist に戻して、実際に 1 件検出して exit 1 になることを確認した。

### ここから得られたこと

**ドキュメントに書いた主張は、それ自体が検査対象になっていないと嘘になる。**
「〜していない」と書くのは簡単だが、書いた時点では真でも、実装が進むと
静かに偽になる。今回は「値を持つファイルを宣言に登録する」という形で、
主張を検査に接続した。

2 件揃うと逸話ではなく型になる。**機械検査は、検査していないものについて
何も報告しない。** 0 件は「準拠している」ではなく「宣言した範囲で違反がない」。
免除リストは沈黙するので、免除の正当性を検査する層が別に要る。

そして**この 2 件はどちらも検査では見つかっていない**。1 件目は DESIGN.md の
記述と実装を人が読み比べて、2 件目は新しい画面を作る人が
「なぜ Table は宣言しなくていいのか」と引っかかって出てきた。
検査の穴は検査では見つからず、**新しい利用者が踏んで初めて出る**。
消費側のリポジトリを実際に作らなければ、どちらも見つからなかった。

## 4. 人手のレビューでしか気づけなかったもの

検査を通過したのに指摘された事項。**ここが機械検査の限界を示す。**

| 指摘 | 検査が見なかった理由 |
| ---- | -------------------- |
| デザインが簡素すぎる | 意匠の質は宣言できない。トークン準拠と美しさは別物 |
| 実在ブランド名の混入（商品名に `Olympus`） | 固有名詞の実在性は DS の管轄外 |
| MUI 依存の DS は DS と言えるのでは | 設計思想への疑義。仕様ファイルには書かれていない |
| 情報量が足りない（商品 3 件） | 「十分な情報量」を機械判定できない |
| 画像ギャラリーが要る | フリマのドメイン知識。DS には image 系の部品が無いことは検査で分かるが、必要だとは分からない |
| 行間が空きすぎ（subgrid の gap 継承） | レイアウトの見た目。実測しないと分からない |

**検査が守るのは「宣言した仕様との一致」だけ**で、「宣言すべきことを宣言したか」
は守らない。ここは人が見るしかない。

## 5. 使ったもの（Skills / MCP / SubAgent / Hook）

### 5.1 MCP

| サーバー | 使ったツール | 用途 |
| -------- | ------------ | ---- |
| `kaze` | `get_token` | トークン値の取得（light/dark 全パレット） |
| | `get_component` | 部品仕様（props / a11y / import 先） |
| | `check_rule` | 禁止パターン照合 |
| | `search` | 部品・トークンの探索（image 系が無いことの確認に使用） |
| `figma` | `use_figma` | code → design のフレーム生成 |
| | `create_new_file` | 新規 Figma ファイル作成 |
| | `get_screenshot` | 生成結果の目視確認 |

`search` の使い方が効いた場面が 1 つある。画像ギャラリーを作る前に
`search('image')` `search('gallery carousel')` を実行し、**DS に該当部品が
無いことを確認**した。無いことを確かめてから独自実装したので、
「DS を無視して勝手に作った」ではなく「DS に無いから作った」と記録できる。

### 5.2 Skills（デザインに使ったもの）

| Skill | 使った場面 |
| ----- | ---------- |
| `frontend-design` | デザイン刷新時。意匠の方向づけ |
| `ui-ux-pro-max` | 同上。product/style/typography/color/ux/stack の各ドメインを検索 |
| `run` | 実機での動作確認（Playwright でブラウザ操作） |
| `update-config` | Hook の settings.json 設定（スキーマを確認してから書いた） |
| `figma-use`（MCP resource） | Figma 書き込み前の必須事前読み込み |
| `figma-create-new-file`（MCP resource） | 新規ファイル作成の手順 |

### 5.3 kaze-ec 側に残したもの（次に触る人のため）

| 種類 | 名前 | 役割 |
| ---- | ---- | ---- |
| Skill | `kaze-ec-new-screen` | 新画面を仕様ファーストで追加する手順 |
| Skill | `kaze-ec-screen-review` | 画面のドリフトを対話で確認 |
| Skill | `kaze-ec-catalog-sync` | `/components` の生成物を再生成 |
| SubAgent | `kaze-ec-design-reviewer` | 大きな UI 差分の審査を委譲 |
| Hook | PostToolUse (`Write\|Edit`) | 編集直後に検査を走らせ違反を差し戻す |

**判定ロジックは `tools/drift/check-drift.mjs` の 1 箇所だけ**に置き、
Skill・SubAgent・Hook はそれを「いつ・誰が・どう使うか」の違いにした。
同じ判定を 3 箇所に書けば、どれか 1 つが必ず古びる。

## 6. 副産物 — kaze-ux 本体のバグを 1 件見つけた

kaze-ec を作るために `/plugin marketplace add BoxPistols/kaze-ux` を使おうとして、
kaze-ux 側の `.claude-plugin/marketplace.json` が壊れていることが分かった。

```
✘ owner: Invalid input: expected object, received string
```

`owner` が文字列だったが、スキーマはオブジェクトを要求する。つまり
**配布の入口が動かない状態だった**。誰も第三者として導入を試していなかった
ために気づかれていなかった。kaze-ux 側で修正済み。

**消費側を実際に作ると、供給側の壊れが見つかる。**
DS を作るだけでは分からない類の欠陥がここにある。

## 7. 結論

### 効いたこと

- **宣言を先に書く強制**が、部品を増やすたびに宣言の更新を強制した（2.3）
- **検査が CI とローカル Hook の両方にある**ので、push 前に止まる（2.4）
- **仕様の単一ソースが外部（kaze-ux）にある**ので、コピーが古びる余地が無い

### 効かなかったこと

- **意匠の質**は一切守れない。トークンに準拠した簡素なデザインは作れてしまう
- **何を宣言すべきか**は守れない。宣言漏れは検出できるが、そもそも
  宣言する対象を人が決めている
- **ドキュメントの主張の真偽**は、それを検査に接続するまで守られない（3）

### 次に同じことをするなら

1. **ドキュメントに「〜していない」と書いたら、その場で検査を書く。**
   書いた時点では真でも、実装が進むと静かに偽になる
2. **検出器は作った直後に意図的に壊して、検出することを確かめる。**
   一度も何も検出していない検出器は、動いている証拠にならない
3. **相対値と絶対値を混ぜない。** ドリフトするのは絶対値だけで、
   相対値（テーマの倍数）は検査対象外にしないと誤検出が出る

## 付録: 検証コマンド

このレポートの主張は、次のコマンドで再現できる。

```bash
# 1. 仕様が実装より先か
git log --format="%h %s" --reverse | head -4

# 2. 検出→修正の対
git show 931a586 --stat && git show 34da328 --stat

# 3. 検査が今も動くか（意図的に壊して確かめる）
sed -i '' "s/main: '#0057B8'/main: '#123456'/" src/theme/theme.ts
node tools/drift/check-drift.mjs   # → 1 件検出、exit 1
git checkout src/theme/theme.ts
node tools/drift/check-drift.mjs   # → 0 件、exit 0

# 4. 宣言規模
node -e "const s=require('./design/screen-spec.json');console.log(s.screens.length,'画面')"
```
