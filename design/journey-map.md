# カスタマージャーニーマップ — どこが繋がっていて、どこが切れているか

[`personas.md`](personas.md) の人物が実際にどう動くか。
**現状の実装で通れる区間と、切れている区間を同じ表に並べる。**

> 「理想の体験」を描いた図は、実装と照合できないので使わない。
> ここでは各段階に **実装状況** の列を持たせ、次に作るものが表から導かれるようにする。

凡例: ✅ 実装済み / 🚧 部分的 / ❌ 未実装

---

## 1. 購入ジャーニー（佐藤・田中 共通）

| # | 段階 | 行動 | 感情・迷い | 必要なもの | 状況 |
| - | ---- | ---- | ---------- | ---------- | ---- |
| 1 | 探索 | 一覧を眺める / 検索する | 「欲しいものがあるか」 | 検索・カテゴリ・タグ絞り込み・並び替え | ✅ |
| 2 | 比較 | 複数の候補を見比べる | 「状態と価格が見合うか」 | 価格・状態バッジ・写真枚数の一覧表示 | ✅ |
| 3 | 検討 | 商品詳細を読む | 「傷はどこか」「出品者は信用できるか」 | 複数写真・説明・出品者情報・関連商品 | ✅ |
| 4 | 保留 | いいねして後で考える | 「まだ迷う」 | お気に入り（ハート） | ✅ 一覧の絞り込み |
| 5 | 決済 | 支払い方法を選ぶ | 「円で払うか暗号資産か」 | 原資トグル・手数料内訳 | ✅ |
| 6 | 待機 | 発送を待つ | 「ちゃんと届くか」 | エスクロー状態の可視化 | ✅ |
| 7 | 完了 | 受取・評価 | 「また買うか」 | 取引完了表示 | 🚧 評価が無い |
| 8 | 振り返り | 購入履歴を見る | 「あれいつ買ったか」 | **購入履歴** | ✅ `/mypage` |

### 切れている区間

残るは **7（完了）の評価**。相手が要るので設計判断が別途必要で、
現状のモックは 1 ユーザーしかいない。

4（保留）はお気に入りを localStorage に保存し、一覧の絞り込みに置いた
（[`decisions/0006`](decisions/0006-favorites.md)）。他の条件と
組み合わせられるので「お気に入りの中でカメラだけ」がそのまま動く。

## 2. 出品ジャーニー（佐藤）

| # | 段階 | 行動 | 感情・迷い | 必要なもの | 状況 |
| - | ---- | ---- | ---------- | ---------- | ---- |
| 1 | 動機 | 「これ売れるかな」と思う | 買い物中・片付け中に思いつく | **どこからでも出品に入れる導線** | ✅ ヘッダーの出品ボタン |
| 2 | 相場観 | 似た商品の価格を見る | 「いくらで出すか」 | 同カテゴリの価格帯 | 🚧 出品時に参考を出すが、件数が少なく相場は出せない |
| 3 | 出品 | 写真・説明・価格を入力 | **「面倒くさい」** | **出品フォーム** | ✅ `/sell` |
| 4 | 公開 | 出品完了 | 「反応あるかな」 | 完了確認 | ✅ 完了画面 → 出品管理 |
| 5 | 観察 | 反応を見る | 「いいねは付いたが売れない」 | **出品管理（一覧・ステータス）** | ✅ `/mypage?tab=listings` |
| 6 | 施策 | 値下げする / 説明を直す | **「値下げすべきか分からない」** | **反応の推移・判断材料** | 🚧 `/effect-lab` は合成データでの検証まで。自分の出品には答えない |
| 7 | 成約 | 売れた | 「発送しなきゃ」 | 通知・発送手続き | ❌ |
| 8 | 振り返り | 売上を見る | 「今月いくら売れたか」 | 売上サマリ | ✅ `/mypage?tab=listings` |

### 切れている区間

1〜5 が繋がり、**出品して、公開して、反応を見返せる**ところまで通った。

2（相場観）は 🚧 のまま。出品時に同カテゴリの出品を参考として出すようにしたが、
**カテゴリあたり 1〜2 件しかないので「相場」は出せない**
（[`decisions/0005`](decisions/0005-price-reference.md)）。件数が少ない旨を
画面に明示している。

残るのは 7（成約通知・発送手続き）だけになった。相手とのやり取りが要る。

6（値下げ判断）はモックの 8 件から効果を出すことができないので、
[`decisions/0003`](decisions/0003-analytics-scope.md) で
**「効果の数字を出す」のではなく「効果が言える条件を満たしているかを出す」**
に問いを組み替えた。

8（売上）は分析ではなく**記録の集計**なので出せた。ただし
合計を 1 つの数字にせず、確定した売上と確定していない売上を分けている
（[`decisions/0007`](decisions/0007-sales-summary.md)）。決済画面が
エスクローを見せているのに売上側で全部足すと、画面ごとに言うことが変わる。

6 を ✅ ではなく 🚧 に留めているのは、`/effect-lab` が答えているのが
**「値下げの効果はこう測る」であって「あなたの出品では値下げが効く」ではない**から。
前者は合成データで示せるが、後者には実ログが要る。ここを ✅ にすると、
画面に出ている数字が出品者の実績として読まれる。

## 3. 役割の往復（C2C 固有）

主ペルソナは購入と出品を行き来する。**その接続点が設計上いちばん重要。**

```
購入ジャーニー 7（完了）───┐
                          ├──→ 出品ジャーニー 1（動機）
探索中に「これ売れるかな」──┘
```

観測できる事実として、出品を思い立つ場面は 2 つある。

| 思い立つ場面 | 必要な導線 | 状況 |
| ------------ | ---------- | ---- |
| 買い物をしている最中（相場を見て） | どの画面からも出品へ | ✅ ヘッダーの出品ボタン |
| 取引が終わった直後（片付けの流れ） | 取引完了画面から出品へ | ✅ 「自分も出品する」 |

**役割を持ち替える場所が「マイページ」**。購入履歴と出品管理を 1 画面に並べ、
切り替えをタブで行う（→ [`decisions/0002`](decisions/0002-role-switching.md)）。
タブの状態は URL に持つので、出品管理を人に共有できる。

**役割の往復が両方向で閉じた。** 買い物中はヘッダーの出品ボタン、
取引が終わった直後は完了画面の「自分も出品する」。出品後は完了画面から
出品管理へ戻すので、`/sell` → `/mypage?tab=listings` も繋がっている。

## 4. 表から導かれる優先順位

**感想ではなく、切れている区間の数と依存関係から決める。**

**済**: マイページ（購入 8 / 出品 5）→ 出品フォーム（出品 3）→ 出品完了導線（出品 4・1）
→ 取引完了からの出品導線（役割往復が閉じた）→ 出品時の参考価格（出品 2 を 🚧 まで）
→ 値下げ効果の検証（出品 6 を 🚧 まで）→ 売上サマリ（出品 8）

| 優先 | 作るもの | 根拠 |
| ---- | -------- | ---- |
| 1 | 評価 | 購入 7。**取引相手が要る**ので設計判断が別途必要 |
| 2 | 成約通知・発送手続き | 出品 7。1 と同じく相手とのやり取りが要る |

残るのは**対人系だけ**になった。現状のモックが 1 ユーザーしか持たないため、
「相手」をどう表現するかの設計判断が先に要る。

売上サマリを作るときに、以前ここへ「`src/lib/causal` の `LogRecord` を
そのまま集計すれば出る」と書いていたのは**誤り**だった。`LogRecord` は
合成データで、集計すると**モックの数字が実績として読まれる**。
実際に使ったのは `SALES`（売却の記録）で、新しく足している
（[`decisions/0007`](decisions/0007-sales-summary.md)）。

## 5. この表の使い方

- **画面を作る前**: 該当する段階の行を読み、「何に困っているか」を確認する
- **画面を作った後**: 状況の列を更新する。**🚧 のまま放置しない**
- **新しい機能を思いついたとき**: この表のどの段階を埋めるかを言えなければ作らない
