# 0003: 出品者向けの分析は、実装より先にスコープと限界を決める

- 状態: 決定（実装は未着手）
- 対象: [`journey-map.md`](../journey-map.md) 出品ジャーニー 6（値下げ判断）
- 経緯: adlumetra（別プロジェクト）の因果推論レイヤーを応用する検討から

## 問題

出品ジャーニーで最大の困りごとは「**値下げすべきか分からない**」
（[`personas.md`](../personas.md) §1）。これに答えるには、
「値下げしたから売れたのか、元々売れる商品だったのか」を分離する必要がある。

単純に「値下げした商品の成約率」を出すと交絡する。値下げする商品は
そもそも売れていない商品なので、比較が成立しない。

## 決定

実装する前に、**言えることの範囲**と**必要なデータ規模**を先に固定する。

### 1. 言えること / 言えないこと

| 区分 | 例 | 可否 |
| ---- | -- | ---- |
| ATT（全体平均） | 「値下げした出品では平均 +6.2pt」 | ✅ |
| CATE（セグメント別） | 「衣類・3,000 円以下では +9.1pt」 | ✅ |
| **ITE（個別）** | **「あなたのこの出品は値下げが効いた」** | ❌ **原理的に不可能** |

**ITE は書かない。** その出品の「値下げしなかった場合」は永久に観測できない
ため、個別の効果は推定できない。文言は「あなたのこの出品**が属する条件では**」
に統一する。

これは実際に一度間違えた判断で、外部レビューで指摘を受けて訂正した。
記録として残す。

### 2. データ規模

| 制約 | 値 |
| ---- | -- |
| 群サイズの下限 | 各群 150 件（500 未満は警告） |
| セグメント分割時 | **セルごとに**下限を満たすこと |

現在の [`listings.ts`](../../src/data/listings.ts) は **8 件**。2 桁足りない。

### 3. データソースを分ける

| ソース | 用途 | 規模 |
| ------ | ---- | ---- |
| `LISTINGS` | 画面に出るカタログ | 8 件のまま |
| 合成取引ログ（未作成） | 分析対象 | 各群 500 件以上 |

**混ぜない。** 混ぜると、モックの数字が実績として読まれる。
画面上でも「何を確かめているところか」を明示する。

### 4. 分割の定義は分析前に宣言する

セグメント（カテゴリ × 価格帯など）の切り方を**結果を見てから変えない**。
変えるなら版を上げる。閾値を後から動かすのは「有意になるまで探す行為」。

同様に、施策が連続値（値下げ幅）の場合は**分析前に閾値を決めて二値化**する
（「10% 以上値下げしたか」）。

## 5. 因果定義（実装前に文章で固定する）

コードより先にこれを埋める。埋まらない項目があるなら設計されていない。

| 項目 | 値 |
| ---- | -- |
| 分析単位 | **出品（listing）** |
| 施策 | 期間内に**出品価格から 10% 以上値下げした**か |
| 成果 | 期間内に成約したか（二値） |
| 期間 | 出品日から 30 日 |
| 比較 | 値下げした出品 vs しなかった出品 |
| 推定量 | **ATT**（実際に値下げした出品にとってどうだったか） |
| 共変量 | カテゴリ / 商品状態 / 出品時の価格帯 / 出品者の過去成約数 / **出品時点の**いいね数 |
| 除外 | 共変量に欠損がある単位 / 同一単位で割付が割れている単位 / 完全一致の重複行 |

### 単位を出品にする理由

**出品者単位にすると割付が定義できない。** 1 人が「値下げした出品」と
「していない出品」を両方持つため。施策が出品に対して行われる以上、単位は出品。

出品管理画面が出品ごとに並んでいることとも一致するが、**それは理由ではない**。
UI の見せ方から分析単位を決めると、施策の実態と食い違う。

### 施策を閾値込みで書く理由

値下げ幅は連続値なので、そのままでは 0/1 に収まらない。**閾値は分析前に決め、
結果を見てから動かさない。** 動かすと「有意になるまで探す行為」になる。

### 共変量と中間変数を型で分ける

| 要因 | 役割 | 理由 |
| ---- | ---- | ---- |
| カテゴリ / 商品状態 / 出品時の価格帯 | confounder | 出品時に確定している |
| 出品者の過去成約数 | confounder | 過去の値なので施策で動かない |
| **出品時点の**いいね数 | confounder | 時点を凍結してある |
| **現在の**いいね数 / 値下げ後の閲覧数 | **mediator** | **値下げ後に動く。入れると効果が消える** |
| 商品写真の質 | unobserved | 観測していない。E-value で感度を出す |

同じ「いいね数」が時点によって役割が変わる。**フィールド名に時点を含める**
（`likesAtListing` と `likesNow`）。名前が同じだと必ず取り違える。
実装では mediator を入れ子にして、共変量を組み立てる関数から見えなくする。

### 5.1 割り当て単位は、申告させずデータから観測する（実装後の追記）

分析単位を出品にしたので、**値下げが何の単位で決まったか**が別途問題になった。
出品ごとに決めるなら独立な割り当ての数は出品数だが、出品者ごとに決めるなら
出品者数しかない。総件数 4000・10 出品/人なら、出品は各群 2000 件あっても
独立な割り当ては各群 200 人分になる。**件数のゲートだけでは通ってしまう。**

3 通り考えて、4 つ目を採った。

| 案 | 内容 | 採否 |
| -- | ---- | ---- |
| 1 | 割り当て単位を設定で受け取り、ゲートがそれに従う | ✕ 実ログで誰かが正しく申告する前提になる |
| 2 | 常に件数で数え、クラスタ数を別項目として表示する | △ 表示だけで止まらない |
| 3 | 今のまま件数で数える | ✕ 通ってはいけないデータが通る |
| **4** | **処置が出品者内で変動しているかをデータから観測し、単位を判定する** | ✅ 採用 |

処置が出品者の中で変動しているかは**観測できる**。申告は要らない。
実装は `src/lib/causal/assignment.ts`、ゲートは `quality.ts` の
`assignment-unit`。件数のゲートは残したまま、独立な割り当て数を別項目にした。

この判断は測定に基づく。総件数 4000・独立データセット 150 本で真の標本 SD を
出し、ブートストラップ推定と突き合わせた結果、**処置が出品者単位でクラスタが
大きい（25 出品/人）とき、出品単位の再標本は区間を 27% 狭く見積もった。**
出品単位の割り当てでは差が出ない。数字と読み方は `assignment.ts` の冒頭に置いた。
